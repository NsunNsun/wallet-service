# Wallet Service

Асинхронный REST API для работы с балансом кошельков пользователей.

**Стек:** Python 3.12, FastAPI, SQLAlchemy 2.0 (async) + asyncpg,
PostgreSQL 16, Alembic, Pydantic v2, pytest, ruff, Docker Compose.

## Быстрый старт

```bash
docker compose up --build
```

Команда поднимает PostgreSQL и приложение. Миграции применяются
автоматически при старте контейнера приложения.

- API: http://localhost:8000
- Swagger UI: http://localhost:8000/docs

Настройки (логин/пароль БД, порт, число воркеров) можно переопределить через
файл `.env` — пример в `.env.example`. Без `.env` используются значения
по умолчанию.

### Тесты

```bash
docker compose --profile test run --rm tests
```

Запускает ruff (проверка PEP8 и форматирования) и pytest против настоящего
PostgreSQL из compose. Тесты создают отдельную базу `<POSTGRES_DB>_test`
и накатывают на неё реальные миграции Alembic (upgrade → downgrade →
upgrade), так что миграции тоже проверяются.

## API

| Метод | Путь | Описание |
|-------|------|----------|
| `POST` | `/api/v1/wallets` | Создать кошелёк с нулевым балансом |
| `GET` | `/api/v1/wallets/{wallet_uuid}` | Получить баланс |
| `POST` | `/api/v1/wallets/{wallet_uuid}/operation` | Пополнить или списать |
| `GET` | `/health` | Проверка работоспособности |

### Пример

```bash
# создать кошелёк
curl -X POST http://localhost:8000/api/v1/wallets
# {"wallet_id":"3fa85f64-5717-4562-b3fc-2c963f66afa6","balance":"0.00"}

# пополнить
curl -X POST http://localhost:8000/api/v1/wallets/3fa85f64-5717-4562-b3fc-2c963f66afa6/operation \
  -H "Content-Type: application/json" \
  -d '{"operation_type": "DEPOSIT", "amount": 1000}'
# {"wallet_id":"3fa85f64-...","balance":"1000.00"}

# получить баланс
curl http://localhost:8000/api/v1/wallets/3fa85f64-5717-4562-b3fc-2c963f66afa6
# {"wallet_id":"3fa85f64-...","balance":"1000.00"}
```

### Коды ответов

| Код | Когда |
|-----|-------|
| `200` | Операция выполнена / баланс получен |
| `201` | Кошелёк создан |
| `404` | Кошелёк не найден |
| `409` | Недостаточно средств, либо превышен максимальный баланс |
| `422` | Некорректный UUID или тело запроса |

## Принятые решения

### Конкурентность

Главное требование — корректная обработка параллельных запросов к одному
кошельку. Изменение баланса выполняется **одним атомарным SQL-запросом**,
без чтения баланса в приложении:

```sql
UPDATE wallets
   SET balance = balance - :amount
 WHERE id = :id AND balance >= :amount   -- условие только для WITHDRAW
RETURNING balance;
```

- `UPDATE` берёт блокировку строки, поэтому параллельные изменения одного
  кошелька PostgreSQL выполняет строго по очереди. Изменения разных
  кошельков друг друга не блокируют.
- На уровне изоляции READ COMMITTED ожидающая транзакция после снятия
  блокировки перепроверяет `WHERE` уже на свежей версии строки. Поэтому
  списание не может увести баланс в минус, а обновления не теряются
  (нет цикла «прочитал → посчитал → записал» с гонкой между шагами).
- Корректность обеспечивает база данных, а не процесс приложения, поэтому
  она сохраняется при любом числе воркеров uvicorn и реплик сервиса.
- Дополнительная защита на уровне схемы: `CHECK (balance >= 0)`.
- Если `UPDATE` не затронул строк, отдельным запросом выясняется причина:
  кошелька нет (404) или не хватает средств (409).

Выбран атомарный `UPDATE`, а не `SELECT ... FOR UPDATE`: результат тот же,
но на один round-trip меньше и блокировка держится минимальное время.

Тесты в `tests/test_concurrency.py` отправляют сотни параллельных запросов
к одному кошельку и проверяют, что ни одно пополнение не потеряно, а число
успешных списаний ровно соответствует доступному балансу.

### Деньги

- Суммы хранятся в `NUMERIC(20, 2)` и обрабатываются как `Decimal`,
  без `float`.
- `amount` должен быть больше 0, не более 2 знаков после запятой и не более
  16 знаков в целой части. `NaN`/`Infinity` отклоняются.
- Баланс в ответе отдаётся строкой (`"1000.00"`), чтобы не терять точность
  на стороне клиента. В запросе `amount` принимается и числом, и строкой.
- Переполнение баланса (выход за `NUMERIC(20, 2)`) возвращает 409, а не 500.

### История операций

Каждая успешная операция записывается в таблицу `wallet_operations`
(тип, сумма, баланс после операции) **в той же транзакции**, что и изменение
баланса. Это даёт аудит и возможность сверки: сумма операций по кошельку
всегда равна его балансу.

### Создание кошелька

В задании нет эндпоинта создания кошелька, но без него сервисом нельзя
пользоваться, поэтому добавлен `POST /api/v1/wallets`.

### Пул соединений

По умолчанию 4 воркера uvicorn × (10 + 10) соединений = не более
80 соединений к БД, что укладывается даже в стандартный лимит PostgreSQL
(100). При пиковой нагрузке запросы ждут свободное соединение из пула,
а не падают с ошибкой.

## Структура проекта

```
app/
  api/v1/wallets.py     # HTTP-слой: роуты
  core/config.py        # настройки из переменных окружения
  db/session.py         # движок и сессии SQLAlchemy
  models/               # ORM-модели
  schemas/              # Pydantic-схемы запросов и ответов
  services/wallet.py    # бизнес-логика и работа с балансом
  services/exceptions.py
  main.py               # сборка приложения, обработчики ошибок
migrations/             # миграции Alembic
tests/                  # тесты эндпоинтов и конкурентности
```

## Локальная разработка без Docker

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
# нужен запущенный PostgreSQL; параметры подключения — в .env
alembic upgrade head
uvicorn app.main:app --reload
pytest
ruff check . && ruff format --check .
```
